# Resume

LaTeX source for my resume, plus the compiled PDF output.

## Compiling

This document uses `fontspec` with the **Spectral** font family, so it must be compiled with **XeLaTeX** (not `pdflatex`). Compile with the wrapper script rather than calling `xelatex` directly:

```
.github/scripts/compile.sh travis_resume.tex
```

It runs `xelatex` twice (needed to resolve hyperlink/outline references) with a fixed `SOURCE_DATE_EPOCH`, which is what makes this safe — see "Committing your own compiled PDF" below for why that matters.

### Fonts

The `fontspec` block expects a `fonts/` folder next to `travis_resume.tex` containing:

- `Spectral-Regular.ttf`
- `Spectral-Bold.ttf`
- `Spectral-Italic.ttf`
- `Spectral-BoldItalic.ttf`

This repo only tracks `.tex`/`.pdf` files at the top level, so the font folder is not included there. Download Spectral from [Google Fonts](https://fonts.google.com/specimen/Spectral) and place the `.ttf` files in a local `fonts/` directory before compiling. (CI gets its copy from `.github/fonts/` — see below.)

## Output

`travis_resume.pdf` is the compiled, up-to-date output and is committed alongside the source. This is the **full** resume, with contact info included — it's what you should send to employers. You don't have to compile it locally before pushing — CI recompiles and commits it automatically if it's out of date (see below). Compiling it locally to preview first is fine too; see "Committing your own compiled PDF" below.

`web_resume.tex` / `web_resume.pdf` are auto-generated by CI (see below) and committed back to this repo. This is the **public** version with email and phone number stripped — it's what gets published to the portfolio site. Don't edit these by hand; they're overwritten on every push.

### Committing your own compiled PDF

It's fine to compile locally to preview before pushing — just always use `.github/scripts/compile.sh` (never call `xelatex` directly). It pins `SOURCE_DATE_EPOCH`, which strips the compile timestamp that would otherwise get embedded in the PDF. Without that pin, your local compile and CI's compile of the *same* `.tex` produce different PDF bytes even though the rendered content is identical — so CI would always see travis_resume.pdf as "changed" and generate its own competing commit, which diverges from whatever you just pushed and forces a manual merge (and PDFs can't be diffed/merged, so it turns into a real conflict).

With the pinned epoch, compiling the same `.tex` always produces byte-identical output. So: preview locally with the script, `git add`/commit/push both files as normal, and when CI recompiles the same content afterward it'll find nothing changed and skip its own commit — no divergence, no conflict.

## Auto-sync to portfolio site

Pushing a change to `travis_resume.tex` (or `.pdf`) on `main` automatically recompiles the full resume, regenerates the redacted web resume, and publishes the latter to [tmb5932.github.io](https://github.com/tmb5932/tmb5932.github.io) — no manual steps needed. You can push just the `.tex` edit and let CI produce both PDFs.

This is handled by [`.github/workflows/sync-to-portfolio.yml`](.github/workflows/sync-to-portfolio.yml), which runs inside the pinned `danteev/texlive:2026-A` container (matching the local TeX Live install, so CI output matches local compiles) and:

1. Triggers on push to `main` when `travis_resume.tex` or `travis_resume.pdf` changes (or manually via `workflow_dispatch`).
2. Compiles `travis_resume.pdf` from `travis_resume.tex` using [`.github/scripts/compile.sh`](.github/scripts/compile.sh), with the fonts in `.github/fonts/` — the same script and fixed `SOURCE_DATE_EPOCH` you use locally, so the output matches a local compile byte-for-byte.
3. Runs [`.github/scripts/make_web_resume.sh`](.github/scripts/make_web_resume.sh), which copies `travis_resume.tex` to `web_resume.tex` and deletes everything between the `% WEB-RESUME:REMOVE-START` / `% WEB-RESUME:REMOVE-END` markers in the header (currently the email and phone line). If you rework the header, keep those markers wrapped around whatever should stay out of the public copy.
4. Compiles `web_resume.pdf` the same way.
5. Commits `travis_resume.pdf`, `web_resume.tex`, and `web_resume.pdf` back to this repo as `github-actions[bot]`.
6. Checks out `tmb5932/tmb5932.github.io`, copies `web_resume.pdf` over `assets/TB_Resume.pdf`, and commits/pushes that change, which triggers a GitHub Pages rebuild (the portfolio site serves directly from `main`, no build step).

The workflow authenticates to the portfolio repo using a fine-grained PAT stored as the `PORTFOLIO_REPO_TOKEN` secret in this repo's Actions settings, scoped only to `Contents: Read and write` on `tmb5932.github.io`. Pushing back to this repo uses the default `GITHUB_TOKEN` with the `contents: write` permission declared in the workflow.
